# 简历工作台项目计划

> 文档性质：项目路线、交付顺序和决策记录
>
> 产品行为依据：[功能设计书](functional-design.md)
>
> 交互行为依据：[交互界面设计书](interaction-design.md)
>
> 技术实现依据：[实现设计书](technical-design.md)

## 1. 计划目的

本计划用于安排简历工作台从当前原型向目标系统演进的工作顺序，记录阶段目标、依赖关系、验收条件和已确认决策。

本文件不重新定义用户功能，也不替代交互或技术设计。功能设计书优先级最高；交互界面设计书负责落实页面和操作行为；实现设计书必须服务于功能与交互设计；本文件只负责回答“先做什么、为什么做、做到什么程度”。

## 2. 项目目标

最终系统应形成一条稳定的简历生产链路：

```text
事实资料与证据
    -> 岗位需求画像
    -> 联动临时简历
    -> 转化并创建正式简历 v1
    -> 正式简历工作副本
    -> 人工/AI 辅助编辑
    -> 不可变正式版本
    -> HTML 与附件 ZIP 交付
```

系统优先保证事实可复用、简历可独立编辑、历史可追溯、证据可交付和技术可扩展，而不是优先扩大推荐算法或投递管理范围。

## 3. 文档与决策层级

```text
功能设计书
  定义产品用途、用户流程和必须满足的行为
        |
        v
交互界面设计书
  定义页面组织、操作入口和状态反馈
        |
        v
实现设计书
  定义架构、数据、接口和实现方案
        |
        v
项目计划
  定义阶段、依赖、交付和验收
```

如果实现设计无法满足功能设计，应修改实现设计和代码，不应降低功能设计的目标。功能设计书中的待确认事项在确认前不得被实现设计擅自固化为不可逆的数据规则。

## 4. 阶段路线

### 阶段 0：设计基线

目标：建立可供用户、开发者和 AI 共同理解的产品与技术基线。

交付内容：

- 功能设计书；
- 交互界面设计书；
- 实现设计书；
- 本项目计划；
- 术语、生命周期、版本和导出规则的一致性检查。

验收条件：

- 功能设计书可以独立解释系统用途和完整工作逻辑；
- 交互界面设计书可以独立解释主要页面、流程和状态；
- 实现设计书没有反向改变产品行为；
- 未决事项均有明确标记和影响范围。

### 阶段 1：领域模型与存储基础

目标：建立能够承载目标功能的数据基础。

工作内容：

- 引入用户/工作区归属边界；
- 建立事实资料、审计、证据、需求画像和招聘机会模型；
- 建立简历身份、工作副本、正式版本和模板版本模型；
- 引入数据库迁移；
- 建立本地文件存储接口和附件元数据；
- 编写旧数据导入和迁移报告。

验收条件：

- 旧资料可以迁移且无静默丢失；
- 同一工作区的简历身份键唯一；
- 历史版本能够保存完整结构化内容、模板和证据清单；
- 文件存储可在本地实现，并通过接口替换为对象存储。

### 阶段 2：事实资料、证据与需求画像

目标：让用户能够维护可复用的事实来源和岗位需求。

工作内容：

- 实现核心事实分类和可扩展条目机制；
- 实现事实修改审计；
- 实现文件、链接和说明形式的证据管理；
- 实现证据与事实、简历区块的关联；
- 实现需求画像和招聘机会的分离建模；
- 实现候选画像指纹和用户确认身份键的流程。

验收条件：

- 同一事实可以被多个画像和简历复用；
- 多个招聘机会可以关联同一画像；
- 证据链接、文件和说明可独立维护；
- 画像变化不会未经用户确认自动拆分简历身份。

### 阶段 3：联动临时简历

目标：提供从事实库到可预览简历的实时工作视图。

工作内容：

- 根据画像加载最新事实资料；
- 保留用户选择状态和内容顺序；
- 保持推荐为辅助能力；
- 提供模板选择和 HTML 预览；
- 提供“转为正式简历”动作。

验收条件：

- 事实变化能够在临时简历重新打开时反映；
- 临时简历视图本身不产生正式版本；转化动作创建“格式化简历、未润色”的正式 `v1`；
- 用户可以忽略推荐结果并手动选择内容；
- 临时简历可以无损转化为正式 `v1` 及以该版本为基线的正式工作副本。

### 阶段 4：正式简历编辑与版本管理

目标：让用户可以人工或 AI 辅助维护可持续编辑的正式简历。

工作内容：

- 实现固定核心区块和模板预设可选区块；
- 实现临时简历只选择事实条目、不编辑文本；
- 实现受控 Markdown 正文；
- 实现来源引用和证据引用；
- 实现工作副本和显式正式保存；
- 实现线性不可变版本；
- 实现历史查看、差异比较、历史编辑和回退；
- 实现事实变化差异提示和手动同步；
- 实现证据变化自动生成 `evidence_sync` 版本；
- 自动证据版本以最近已保存版本为基线，不包含未保存正文；
- 实现未保存工作副本的证据更新待处理状态和合并失败状态；
- 实现新身份从当前正式版本复制工作副本。

验收条件：

- 正式正文独立于事实库，但来源可追溯；
- 历史版本不能被修改或覆盖；
- 回退会形成新的当前版本；
- AI 不能绕过用户正式保存；
- 证据变化会自动进入带原因的版本历史。

### 阶段 5：模板、预览和交付

目标：形成稳定、可复现的 HTML 和附件交付物。

工作内容：

- 实现模板和模板版本管理；
- 实现结构化内容到 HTML 的渲染；
- 实现外链可点击和附件相对路径；
- 实现 HTML、附件目录和 `manifest.json` 的 ZIP 导出；
- 增加导出复现和附件校验。

验收条件：

- 历史版本在当前资料变化后仍可复现；
- 导出包包含准确的 HTML、附件和清单；
- 未选择的证据不会被导出；
- 模板更新不会改变历史版本的渲染结果。

### 阶段 6：AI 与未来多用户能力

目标：在不破坏人工流程和隐私边界的前提下增加辅助能力。

工作内容：

- 实现可插拔 AI Provider；
- 实现显式发送范围确认；
- 实现 AI 修改差异、应用和放弃；
- 实现 AI 请求和变更记录；
- 完善用户、工作区、权限和会话；
- 验证 PostgreSQL、对象存储和异步任务实现。

验收条件：

- AI 服务不可用不影响人工编辑；
- AI 不能虚构事实或证据；
- 业务资源不能跨工作区访问；
- 本地实现和未来服务端实现遵守同一产品行为。

## 5. 已确定的产品决策

| 主题 | 决策 |
| --- | --- |
| 功能优先级 | 功能设计书高于实现设计书和项目计划 |
| 交互优先级 | 交互界面设计书在功能设计书约束下高于实现设计书和项目计划 |
| 首页总览 | 系统启动后进入扁平化首页总览，不显示固定左侧导航，也不存在独立工作台模块 |
| 主要模块 | 首页入口只有资料库、岗位画像和简历工作台；模块首页通过功能卡片进入具体工作区 |
| 资料库入口 | 资料库首页只有资料维护核心入口，证据管理属于资料维护子功能 |
| 简历工作台入口 | 常态优先创建临时简历；存在未完成副本时优先继续上次工作；正式简历列表位于下方 |
| 临时简历开始 | 创建临时简历时第一步选择岗位画像 |
| 事实条目 | 事实记录保持中立，岗位特化在正式简历中完成 |
| 临时简历 | 实时读取事实库，不产生正式版本 |
| 临时简历编辑 | 只能选择事实条目和预览，不允许修改文本 |
| 正式简历 | 正文独立编辑，但保留来源关系 |
| 正式简历结构 | 核心固定区块加模板预设可选区块，不允许自由新增结构 |
| 正文格式 | 纯文本加段落、粗体、斜体、无序列表和链接 Markdown 子集 |
| 正式版本 | 线性不可变，支持差异、历史编辑和回退 |
| 回退 | 通过新版本实现，不覆盖历史 |
| 证据 | 面向招聘者验证，可为链接、文件或说明 |
| 证据引用 | 展示方式保存在简历区块引用关系上，证据本体可复用 |
| 证据文件 | PDF、PNG、JPEG、WEBP；单文件 10 MB，单附件包 100 MB |
| 证据变化 | 影响交付内容时自动生成 `evidence_sync` 版本；内部备注变化不生成 |
| 证据自动版本 | 以最近已保存版本为基线，不包含未保存正文 |
| AI | 可直接修改工作副本，但不能直接正式保存 |
| AI 默认范围 | 当前区块的最小必要上下文，不发送附件原文件、未选事实或其他简历 |
| 岗位组织 | 需求画像与招聘机会分离 |
| 新身份 | 用户确认后创建，默认复制当前正式版本 |
| 身份指纹 | 岗位方向、核心技术要求、简历策略；归一化后生成候选值，用户可编辑且唯一 |
| 推荐 | 保持辅助定位，不作为系统核心 |
| 输出 | HTML 主文档加证据附件 ZIP |
| 导出命名 | 可读名称加稳定版本号 |
| 模板 | 工作副本可以切换模板，保存后形成新版本；历史版本固定模板版本 |
| 临时转正式 | 转化时立即创建正式 `v1`，版本原因是“格式化简历、未润色”；后续正式保存追加新版本 |
| 待处理入口 | 只承担通知和跳转，不提供批量处理 |
| 导出警告 | 存在未处理警告时默认阻止导出；用户明确确认风险后可以强制导出 |
| 来源差异 | 来源侧栏采用上下对照，并在对应位置使用行内差异标记 |
| AI 编辑界面 | 第一版只展示原文与建议差异，不额外进行风险判断；只修改工作副本 |
| 编辑器快捷操作 | 保留基础通用操作，不定义复杂专用快捷键体系 |
| 窗口范围 | 第一版只支持桌面宽窗口，不承诺窄窗口或移动端适配 |
| 模板预览 | 预览图用于查看样式，选中模板后在工作副本中实时渲染实际简历 |
| 证据失效处理 | 替换、保留和移除逐项处理，不提供批量修改 |
| 前后端 | 暂定 TypeScript SPA + REST API，具体工具可后续调整 |
| 存储 | 本地优先，数据库和文件存储可替换 |
| 多用户 | 从数据模型预留，当前未来工作区按平等成员处理 |
| 投递管理 | 第一阶段只记录岗位来源和关联，不做完整投递跟踪 |

## 6. 待确认事项

以下事项不阻塞总体设计，但在对应阶段开始前必须定稿：

1. 证据文件的保留期限、附件展示顺序和清单字段。
2. AI Provider 的具体服务商、默认脱敏策略和服务配置。
3. 未来工作区成员的登录、邀请和审计方式。
4. 标准词库和 AI 判断如何补充候选身份指纹，但不能绕过用户确认。

交互界面设计书已经建立，首页总览、三个业务模块、临时简历选择页、正式简历编辑器、来源与证据面板、版本历史、差异比较、AI 修改确认和导出页面以该文档为准。仍待确认的交互细节包括首页业务状态摘要、入口视觉形式、正式简历列表字段、模块卡片样式、待处理通知细节、强制导出记录、AI 差异视觉样式、基础快捷键清单、模板预览尺寸、导出摘要布局和证据逐项确认流程。

下一阶段优先完成待确认交互细节的讨论；确认后更新交互界面设计书，并检查功能设计书和实现设计书是否需要同步调整。

每个待确认事项都必须在实现前更新功能设计书，并同步检查技术设计书是否仍然满足功能要求。

## 7. 迁移工作项

当前工作区原型迁移到目标系统时，按以下顺序处理：

1. 备份现有 SQLite 数据库和 HTML 输出目录。
2. 将个人资料、教育、经历、技能和成果导入事实资料库。
3. 将现有岗位数据转换为需求画像或招聘机会，并保留原始字段。
4. 将现有模板导入模板实体和模板版本。
5. 将旧简历记录标记为来源不完整的历史记录，不能伪装成完整新版本。
6. 输出未映射字段、缺失来源和不完整证据报告。
7. 验证迁移后的数量、内容、来源和 HTML 渲染。

迁移工作不得覆盖原始数据库，也不得以“字段暂时没有 UI”为理由丢弃内容。

## 8. 变更管理

产品功能变更流程：

1. 先修改功能设计书并说明用户价值和行为影响。
2. 检查是否影响对象关系、生命周期、版本和导出规则。
3. 更新实现设计书，选择满足新功能的技术方案。
4. 更新本计划中的阶段、依赖和验收条件。
5. 最后进入代码实现和测试。

任何只修改技术实现、不改变用户行为的调整，可以只更新实现设计书和相关阶段记录；任何影响用户工作逻辑的调整，都必须先更新功能设计书。
