# 简历工作台功能设计书

> 文档性质：产品功能与行为基准
>
> 适用对象：使用者、产品设计者、开发者和 AI
>
> 文档状态：目标设计；不以当前代码实现限制产品行为

## 1. 文档地位

本文档定义简历工作台是什么、解决什么问题、有哪些功能，以及这些功能在用户看来应当如何工作。

本文档是项目中关于产品行为的最高优先级依据。实现设计、代码结构、数据库选型和前端技术都必须服务于本文档规定的功能目标。如果技术实现与本文档冲突，应调整技术实现；不能为了迁就实现而改变用户应获得的功能。

本文档描述的是目标系统，不是当前版本的代码说明。当前实现只能作为后续迁移和兼容工作的参考。

### 1.1 2026-09 绑定修订

- 默认简历模板以 `output/默认简历成品目录/机器人数据采集与数据标注_初版.html` 为视觉和信息架构基准；其页面必须为固定 A4，内容允许续页但不得拉长纸张。
- 临时简历通过点击画布区块打开居中选择卡片来选择事实；正式简历采用“只读 A4 预览 + 点击区块打开编辑卡片”，不在纸面内直接放置编辑控件。
- 资料库首页使用分类入口总览和全局搜索，分类页使用可审阅表格；每条事实都提供证据数量和证据管理入口。
- 未进入正式历史的数据可永久删除；被正式历史引用的数据必须进入可恢复回收站。

### 1.2 2026-09 实施基线

- 临时简历初始只显示模板栏目名称和一张 A4 画布，不自动选择事实资料；选择内容后才按固定 A4 页面续页。
- 默认经典模板的侧栏只承载基础信息、技能和成果，正文承载个人简介、项目实践、教育和链接，禁止重复渲染。
- 事实资料使用公共主表与分类明细表，旧 `content` 仅作为迁移兼容快照保留。
- 第一阶段正式导出为独立 HTML 文件；ZIP 附件包仍按后续阶段实现。

## 2. 产品定位

### 2.1 要解决的问题

求职者通常拥有大量分散的个人经历、项目材料、技能、成果和证明文件，但每个岗位需要强调的内容不同。直接复制和修改多份简历会带来以下问题：

- 事实资料重复维护，容易出现信息不一致；
- 不同岗位版本之间难以追踪改动；
- 项目经历、技能和证明材料的来源不清晰；
- 人工润色后的正式简历容易失去与原始事实的关联；
- 简历文件、附件和历史版本难以统一管理。

简历工作台要解决的是“事实资料如何沉淀、岗位要求如何组织、简历如何特化、修改如何追踪和成果如何交付”这一整条工作链路。

### 2.2 产品目标

系统应当让用户能够：

1. 在一个事实库中维护可复用的个人资料和经历。
2. 为不同岗位方向建立可复用的岗位需求画像。
3. 根据岗位需求快速形成与事实库联动的临时简历。
4. 将临时简历转为独立正式简历，并在正式简历工作副本中进行人工或 AI 辅助润色。
5. 在不破坏历史版本的前提下继续编辑正式简历。
6. 追踪正式简历内容的事实来源和可验证证据。
7. 输出可直接查看、打印和发送的 HTML 简历及证据附件包。

### 2.3 非目标

第一阶段不把系统定义为：

- 自动替用户完成求职决策的系统；
- 以推荐算法为核心的内容生成系统；
- 完整的招聘投递管理系统；
- 默认依赖云端 AI 的在线服务；
- 只能生成一次、不能持续编辑的简历导出器。

## 3. 核心概念

### 3.1 事实资料

事实资料是用户真实拥有或经历过的信息，是简历内容的基础来源。事实资料不针对某一个岗位书写，内容应尽量客观、可复用和可验证。

核心分类包括：

- 个人信息：姓名、联系方式、城市、身份、毕业时间和可到岗安排；
- 教育经历：学校、专业、学历、时间、课程和成绩优势；
- 经历：项目、竞赛、课程、实习、社团或其他实践；
- 技能：技能名称、分类、熟练程度和实际使用场景；
- 成果：奖项、证书、排名、作品和阶段性结果；
- 链接与作品集：GitHub、个人主页、演示地址、视频或其他可访问资源。

系统应支持后续增加证书、语言、出版物等事实分类，但新增分类不应破坏既有简历模板和版本。

### 3.2 证据

证据是帮助招聘者确认简历内容的材料，不是只供系统内部审核的隐私记录。证据可以是：

- 文件，例如证书、截图、报告和证明材料；
- 链接，例如 GitHub 项目、在线作品、网页或视频；
- 说明，例如证据的名称、用途、来源和展示提示。

证据可以与事实资料或正式简历内容区块关联。链接应当能够在正文中以可点击超链接展示；图片和文件默认作为附件随交付包提供。证据不应在没有用户选择的情况下自动暴露在简历正文中。

### 3.3 岗位需求画像

岗位需求画像描述一类稳定的求职方向，是简历身份的主要业务依据。它不等于某一家公司的招聘信息，也不等于一次投递记录。

画像至少包含：

- 岗位方向；
- 核心技术要求；
- 一般能力要求；
- 主要职责；
- 简历策略或强调方向；
- 可供参考的原始 JD；
- 来源和备注。

系统可以根据画像计算候选身份指纹，但最终身份由用户确认。候选指纹当前只使用岗位方向、核心技术要求和简历策略，并按后文规定进行标准化；未来词库或 AI 判断可以补充候选值，但不能绕过用户确认。

### 3.4 招聘机会

招聘机会是岗位需求画像的具体来源或使用场景，包含公司、岗位名称、原始 JD、链接和来源备注。多个招聘机会可以关联同一个需求画像，从而避免因为公司不同而重复创建近似简历。

第一阶段只维护来源与关联信息，不实现投递状态、联系人、面试阶段和提醒等完整求职跟踪功能。

### 3.5 联动临时简历

联动临时简历是根据事实库和需求画像实时形成的工作视图。它的作用是帮助用户快速判断哪些资料适合某个岗位，并作为正式简历的起点。

联动临时简历具有以下特征：

- 读取事实库的当前内容；
- 读取当前需求画像和模板；
- 可记录用户的内容选择和排列意图；
- 不形成正式版本历史；
- 事实资料变化后，重新打开时反映最新内容；
- 不承担最终对外交付职责。

临时简历可以保存为临时工作状态，以便用户继续选择内容，但临时状态不等同于正式版本。

### 3.6 正式简历

正式简历是经过人工或 AI 辅助特化、可以持续编辑和对外交付的独立简历文档。它从联动临时简历产生，但不再自动使用事实资料覆盖正文。

正式简历仍然保留每个内容区块与事实资料、证据的来源关系，用于追溯、差异提示和手动同步。正文内容与事实资料是独立的，事实条目发生普通修改时，正文不会自动变化。

### 3.7 工作副本与正式版本

工作副本是用户正在编辑但尚未正式保存的内容。正式保存时，系统把工作副本记录为一个不可变版本。

正式版本具有线性历史，支持查看、比较、编辑和回退。历史版本不能被直接覆盖；从历史版本回退或编辑后，必须保存为新的版本。

### 3.8 简历身份

简历身份代表一份围绕特定需求画像维护的正式简历文档。身份键与导出文件名分离：身份键用于系统判断是否为同一份简历，文件名用于用户阅读和交付。

系统可以根据岗位方向和核心技术要求生成候选身份指纹，但用户必须确认身份。用户也可以输入或修改身份标识。公司名称和单条招聘机会默认不是简历身份的唯一依据。

候选身份指纹只使用岗位方向、核心技术要求和简历策略。标准化规则为：去除首尾空格、合并连续空白、英文统一小写、技术要求去重并排序，中文保留原文；简历策略按归一化后的完整文本参与计算。未来可以增加标准词库或 AI 判断，但不能绕过用户确认。

当画像的重要岗位方向或技术要求发生变化时，系统显示差异并由用户选择：

- 继续维护当前简历身份；或
- 创建新的简历身份。

创建新身份时，默认将当前正式版本复制到新身份的工作副本，原身份及其历史保持不变。

## 4. 功能模块

### 4.1 事实资料库

用户可以新增、编辑、归档和查看事实资料。每条资料应支持：

- 核心内容；
- 分类；
- 标签或关键词；
- 与证据的关联；
- 来源说明；
- 当前状态；
- 创建、修改和归档时间。

事实资料的修改更新当前值，并记录审计信息。事实资料可以被多个临时简历和正式简历引用。

事实资料的删除应优先采用归档或软删除，避免破坏正式简历的来源关系。被归档的资料不能出现在新的临时简历推荐中，但历史正式版本仍应能查看其快照。

### 4.2 证据管理

用户可以为事实资料或正式简历区块添加文件、链接和说明，并设置展示方式：

- 不展示；
- 在正文中作为链接展示；
- 在正文中引用附件；
- 作为附件随简历交付。

证据本体只保存材料信息，展示设置保存在具体的“简历区块-证据”引用关系上。同一份证据可以在不同事实条目、简历区块和简历身份中采用不同展示方式。

第一版文件证据只支持 PDF、PNG、JPEG 和 WEBP。单文件最大 10 MB，单份简历附件包最大 100 MB；超过限制或格式不支持时拒绝上传。证据保留校验和，不允许物理删除，只能标记失效或归档。

只有影响对外交付内容的证据变化才自动生成带“证据同步”标记的新版本，包括正文链接、附件文件、附件说明、引用关系和证据失效。仅修改内部备注不生成版本。自动版本只同步证据引用、附件清单和 `manifest`，不自动改写正文。

### 4.3 岗位需求画像与招聘机会

用户可以创建和编辑需求画像，并为画像维护核心技术要求、一般要求、职责、原始 JD 和来源。

用户可以把多个招聘机会关联到同一画像。招聘机会发生变化时，系统应显示其与画像的差异，但不自动改变正式简历身份。

当用户认为招聘机会已经代表新的技术要求组合时，可以基于当前画像创建新画像，并触发新简历身份确认流程。

### 4.4 推荐与选择

推荐只是内容选择辅助，不是产品核心目标，也不能替用户决定最终内容。系统可以继续使用标签匹配对事实资料排序，并显示匹配依据。

推荐结果必须满足：

- 用户可以查看为什么推荐某条内容；
- 用户可以忽略推荐并手动选择内容；
- 推荐失败或没有匹配结果时，用户仍然可以正常创建简历；
- 推荐结果不能自动修改事实资料和正式简历正文；
- 推荐规则变化不能改变既有正式版本的内容。

### 4.5 联动临时简历工作流

用户从岗位画像模块选择需求画像后进入创建流程；招聘机会只作为画像的来源或上下文：

1. 系统加载最新事实资料、画像和可用模板。
2. 系统提供内容选择、顺序和初始排版预览。
3. 用户可以调整选择结果，并保存临时工作状态。
4. 用户可以预览实时生成的 HTML；临时简历不开放文本编辑、人工改写或 AI 润色。
5. 用户可以选择“转为正式简历”。

临时简历视图本身不进入正式版本历史。事实库更新后，临时简历再次打开时应使用最新事实内容；已保存的选择意图可以继续使用，但不存在的或已归档的资料应明确提示。

用户确认“转为正式简历”时，系统立即根据临时简历的结构和选择结果创建正式简历 `v1`。该版本原因标记为“格式化简历、未润色”，并作为当前正式版本进入版本历史；随后用户进入正式简历工作副本继续编辑。临时简历本身仍不属于正式版本。

### 4.6 正式简历编辑

正式简历由固定结构区块组成。核心区块包括：

- 基本信息；
- 求职目标；
- 个人简介；
- 教育经历；
- 项目与实践经历；
- 技能；
- 成果；

模板可以定义可选区块，例如籍贯、政治面貌、独立作品集和链接。用户只能启用或关闭模板已经提供的可选区块，不能自由新增结构、改变区块顺序、修改布局或编辑模板几何样式。用户可以修改固定区块中的内容和显示状态。

正式简历正文以纯文本和结构字段为主，支持受控 Markdown 子集：段落、粗体、斜体、无序列表和链接。不支持标题、表格、图片、HTML、脚本和自定义 CSS。正式简历中的文字可以与事实资料不同；无事实来源的文字必须标记为用户内容或 AI 内容，不能伪装成事实来源。

v1 实现中，正式简历工作区的 A4 页面只负责忠实预览；用户点击区块打开居中编辑卡片，右键打开快捷菜单，编辑控件不再嵌入 A4 纸面，避免浏览器原生 `textarea` 滚动条和缩放手柄干扰预览。

用户编辑的是工作副本。临时简历转化时已经创建的格式化初版是 `v1`；之后点击正式保存时，系统基于当前工作副本生成新的不可变版本并将其设为当前版本。未保存的编辑可以放弃，不应修改历史版本。

### 4.7 AI 辅助

AI 是正式简历编辑的辅助工具，不是自动发布工具。AI 可以根据用户选定的岗位画像、事实来源、证据和当前区块内容修改工作副本。

AI 功能必须满足：

- 用户明确选择允许发送的数据范围；
- AI 可直接修改工作副本，但不能直接生成用户未确认的正式版本；
- 用户可以查看 AI 修改前后的差异；
- 系统记录模型、请求范围、输出和变更来源；
- AI 服务不可用时，人工编辑流程仍然可用；
- AI 不得虚构事实、指标、职责、奖项或证据。

### 4.8 版本管理

正式简历版本使用线性编号，例如 `v1`、`v2`、`v3`。每个版本保存完整的结构化内容、来源关系、证据清单、模板版本和导出相关信息。

用户可以：

- 查看版本列表和版本原因；
- 查看任意两个版本之间的差异；
- 从任意历史版本创建工作副本；
- 将历史版本回退为当前工作副本；
- 保存工作副本形成新版本。

回退不是覆盖历史版本，而是以历史版本内容创建新的当前版本。系统不支持传统 Git 的分支合并和冲突合并。

以下事件产生正式版本：

- 临时简历转化为正式简历并创建格式化初版 `v1`；
- 用户正式保存已有正式版本的工作副本；
- 用户确认回退并保存；
- 用户确认从当前身份创建新的身份并保存首个版本；
- 影响交付内容的证据发生变化并自动同步。

普通事实资料变化只产生差异提示，不自动修改正式正文，也不自动生成版本。

如果证据变化时存在未保存的人工或 AI 工作副本，自动版本从最近一个已保存版本生成，只同步证据关系和附件清单，不包含未保存正文。工作副本原样保留并显示证据更新待处理状态；无法安全合并时，不覆盖工作副本，等待用户处理。

### 4.9 模板管理

模板是内容之外的呈现方式。用户可以查看可用模板，系统可以新增、复制、启用和更新模板。

模板应当版本化。正式简历版本必须固定使用的模板版本，模板后续更新不得改变历史版本的渲染结果。更换模板属于正式简历工作副本的变化，正式保存后形成新版本。

用户可以在正式简历工作副本中切换模板。模板切换和由模板带来的可选区块变化，在正式保存后形成新版本；历史版本继续固定使用原模板版本。

### 4.10 HTML 与附件导出

当前首版先实现独立 HTML 主文件和严格 A4 页面；附件 ZIP、`manifest.json` 和证据附件引用在后续交付阶段实现。

系统的主交付格式为 HTML。导出操作生成一个 ZIP 包，至少包含：

```text
resume.html
attachments/
  ...证据文件...
manifest.json
```

HTML 中：

- 外部链接保持可点击；
- 附件引用使用 ZIP 内的相对路径；
- 引用图片或证明文件的文字应明确提示“见附件图 X”或等效说明；
- 用户未选择输出的证据不得进入正文或附件包。

导出包必须对应一个确定的正式版本。重新导出同一版本时，内容和附件清单应保持一致；证据同步后导出新版本，不能静默覆盖旧版本的历史含义。

## 5. 典型工作流

### 5.1 从事实资料到临时简历

```text
维护事实资料
    -> 创建或选择需求画像
    -> 关联招聘机会（可选）
    -> 查看推荐和事实来源
    -> 选择内容并预览联动临时简历
```

### 5.2 从临时简历到正式简历

```text
临时简历
    -> 选择资料库事实、调整顺序并预览
    -> 转为正式简历，立即形成“格式化简历、未润色”的 v1

正式简历工作副本
    -> 人工编辑或调用 AI 辅助
    -> 查看来源、证据和差异
    -> 用户正式保存
    -> 形成新的不可变版本
```

### 5.3 正式简历持续迭代

```text
当前正式版本
    -> 编辑工作副本
    -> 可查看事实变化和证据变化
    -> 可从历史版本恢复内容
    -> 用户保存
    -> 形成新的不可变版本
```

### 5.4 新岗位需求身份

```text
画像字段发生重要变化
    -> 系统计算候选差异
    -> 用户选择继续当前身份或创建新身份
    -> 默认复制当前正式版本
    -> 在新身份工作副本中调整
    -> 保存为新身份的 v1
```

## 6. 状态与规则

### 6.1 简历状态

| 状态 | 含义 | 是否进入正式历史 |
| --- | --- | --- |
| 临时工作状态 | 与事实库联动的选择和预览状态 | 否 |
| 工作副本 | 正式简历当前未保存修改 | 否 |
| 正式当前版本 | 当前对外可交付版本 | 是 |
| 正式历史版本 | 不再作为当前版本但可查看和恢复的版本 | 是 |

### 6.2 联动与独立规则

| 内容 | 临时简历 | 正式简历正文 | 正式简历来源/证据 |
| --- | --- | --- | --- |
| 事实资料普通修改 | 实时反映 | 不自动覆盖 | 显示差异提示 |
| 事实资料归档 | 提示并从新选择中移除 | 历史正文保留 | 标记来源不可用 |
| 证据修改 | 实时反映 | 正文不被重写 | 自动同步并生成版本 |
| 模板修改 | 使用当前模板版本 | 固定历史模板版本 | 不影响历史 |
| AI 修改 | 不直接写入正式正文 | 修改工作副本 | 记录变更来源 |

### 6.3 不可违反的产品规则

1. 事实资料是来源，不应被岗位简历的润色内容反向污染。
2. 正式简历正文可以独立编辑，但不能丢失来源追溯能力。
3. 历史正式版本不可被覆盖。
4. 回退必须产生新的当前版本。
5. AI 不能绕过用户正式保存。
6. 推荐不能替代用户选择。
7. 证据对外可验证，但必须由用户选择展示范围。
8. 历史版本应能够复现其正式保存时的正文、模板和证据清单。

## 7. 验收标准

功能设计完成后，至少应能验证以下场景：

- 用户可以维护事实资料，并在多个需求画像中复用同一条事实。
- 用户可以把多个招聘机会关联到一个需求画像。
- 临时简历能读取最新事实资料，且不产生正式版本。
- 用户可以把临时简历转成正式工作副本；转化立即形成原因标记为“格式化简历、未润色”的正式 `v1`，之后可以独立修改正文。
- 正式简历内容区块可以保留来源关系和用户/AI 内容标记。
- AI 可以修改工作副本，但不能直接形成正式版本。
- 临时简历转化立即产生正式 `v1`；后续用户正式保存产生不可变新版本。
- 任意两个版本可以比较；从历史版本恢复后再次保存会产生新版本。
- 普通事实变更只提示差异，不自动覆盖正式正文。
- 证据变更自动产生带原因标记的新版本。
- 用户确认新需求画像后，新简历身份继承当前版本但拥有独立历史。
- 导出包包含 HTML、附件和清单，HTML 链接可点击且附件引用可定位。
- 模板更新不会改变历史正式版本的渲染结果。
- 临时简历不能直接编辑文本，只能选择事实条目并预览。
- 正式简历只允许编辑固定区块和模板已有的可选区块。
- Markdown 仅支持段落、粗体、斜体、无序列表和链接。
- 证据文件限制为 PDF、PNG、JPEG、WEBP，单文件不超过 10 MB，单份附件包不超过 100 MB。
- 证据变化期间未保存的正文不会进入自动证据版本。

## 8. 待确认事项

以下事项可以在不改变整体产品原则的情况下继续细化：

1. 标准词库和 AI 判断如何补充候选身份指纹，但不能绕过用户确认。
2. 证据文件的保留期限、附件展示顺序和清单字段。
3. AI Provider 的具体服务商、默认脱敏策略和服务配置。
4. 未来工作区成员的登录、邀请和审计方式；当前按平等成员预留。

这些事项应在不违背本文档产品原则的前提下确定。若后续实现设计提出不同方案，应回到本文档评估其是否仍能完整呈现上述功能。
